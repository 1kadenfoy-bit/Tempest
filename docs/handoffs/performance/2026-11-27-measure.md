# Performance: measuring the app, the report and the fix list

Nov 27, 2026 · branch `claude/tempest-performance` · ready to integrate (Kaden asked to merge)

## What changed
Nothing in how the app looks or behaves. This adds a way to measure it, the
measurements, and a ranked fix list for the other sections.

- **The `?perf` test mode.** Open the app with `?perf` added to the address
  and it runs a two-minute tour by itself (pan, pinch, 3D tilt, dragging the
  time, play, every layer, every panel, a quiet spell), then shows a results
  card with each of Kaden's targets. "Copy numbers" copies the full results as
  text. `?perf&off=bloom` (or `haze`, `shadows`, `water`, `zones`, `labels`,
  `hillshade`, `contours`, `fills`) switches one feature off for that run only;
  nothing is saved. Without `?perf` the app loads none of it.
- **The report:** `docs/reports/performance/report.md`. Each target passed or
  failed with Kaden's iPhone 12 numbers (seven runs) beside the build
  machine's, the causes ranked, each feature's cost, loading, "then against
  now" (Nov 18, Nov 22, today), a fix list of 13 with owners, and 7 trade-offs
  for Kaden to decide (none made).
- **Build-machine tools** in `tools/perf/` to run the same tour, feature by
  feature, with a code profile, a download log and older versions.

## What to try after it is integrated
1. Open `https://1kadenfoy-bit.github.io/Tempest/?perf` in Safari, do not touch
   the screen for about two minutes, and read the card.
2. Open it again with `?perf&off=bloom`: the same tour with the glow off.
3. Open the app normally: nothing is different.

The installed app cannot take `?perf` (it always opens at its plain address).

## Files
- **Own files changed:** `app/perf/`, `tools/perf/`, `docs/reports/performance/`,
  this note.
- **Shared files changed** (the lead's), and why:
  - `app/main.ts`: one line near the top that loads `app/perf/` only when the
    address has `?perf` (a separate file the browser never downloads
    otherwise). The test mode needs the map, the time cursor and the settings,
    which only `main.ts` holds.
- **Hooks in other sections' files:** none. The feature switches in
  `app/perf/switches.ts` hide map layers by id and set the Maps section's
  tuning values (`app/map/tuning.ts`) for that run only, from the test mode's
  own file.
- **New files no section owns yet:** none (all under the Performance paths in
  `sections.json`).
- **Note for the installed app:** its service worker keeps every built file,
  so it now also keeps the test mode's files (about 15 kB), unused unless
  `?perf` is asked for.

## Connection points
- **Used:** `S` from `app/state.ts` (map, cursor, layers, active layer,
  settings, 3D), the body markers the app sets for its tests (`data-fill`,
  `data-series`, `data-idle`, `data-air-fill`, `data-avalanche-map`), the
  buttons' ids.
- **Changed or added:** `window.tempestPerf` exists only in `?perf` mode.
- **Needs from other sections:** the fix list in the report (section "Fix
  list"), in order:
  1. Maps: the glow drawn on the graphics chip, without copying each frame back
     (same look; Maps rules 19, 21, 23).
  2. Weather on the map: rain or snow at real height worked out off the main
     thread, and only when its inputs changed (decision "Rain or snow", Nov 16).
  3. Maps: mountain shadows off the main thread, without the PNG round trip.
  4. Maps: one terrain-height reader, off the main thread, shared.
  5. The lead with Weather on the map: draw each time step already in memory at
     once while the time is dragged.
  6. Data: the map's requests do not wait silently up to 90 s for the
     allowance; the map files answer at once (decision "Temperature data", M4).
  7. Weather on the map: a failed fill tries again by itself.
  8. The lead with Data: start the weather while the map loads.
  9. Data: read a weather file's variables together.
  10. Weather on the map: wind's ground smoothing off the main thread.
  11. Interface and the lead: no timer redraws while untouched.
  12. Data: the installed app's first start fetches the test pages' files last.
  13. Effects: the clouds' cost when switched on.

## Checks
`npm run check:section -- performance --no-browser`: area OK (one shared file,
`app/main.ts`, explained above), typecheck, lint and 67 unit test files (377
tests) pass. The section has no browser test of its own yet (`e2e/perf.spec.ts`,
the lasting check, is the next job), so the browser step was not run by the
check; instead `e2e/shell.spec.ts` and `e2e/details.spec.ts` were run on
recorded weather with the test-mode line in place: 19 passed.

## Kaden's rules added or changed
None. `docs/wishes/performance.md` is as the lead wrote it (targets 1 to 8).

## Decisions made, and anything unsure
- The tour moves the map with the map's own camera calls, not fake touches
  (iOS does not allow them); the drawing per frame is the same as under a
  finger.
- Kaden's runs 1, 2, 4 and 5 were with Low Power Mode on (30 fps cap); runs 3,
  6 and 7 at full speed count against the targets.
- Run 5 is taken as the `?perf&off=bloom` run from the order of the links
  given; runs 6 and 7 record their address.
- The build machine draws in software; its frame rates compare features and
  versions, not targets. Its processor runs the app's code at about the phone's
  speed in Low Power Mode and 1.7 times slower than the phone at full speed
  (the tour's Yardstick).

## Data, sources and terms
No new source. The build machine opened the real site with live weather three

weather. Open-Meteo's counting rule and limits were checked in the website's
own source on GitHub (open-meteo.com is not reachable from the build machine).
